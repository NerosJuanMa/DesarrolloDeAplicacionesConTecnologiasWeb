Nomenclaturas en Desarrollo Web: Introducción

En programación profesional, elegir bien el nombre de las cosas es tan importante como que el código funcione. Una buena nomenclatura ayuda a que todos los miembros del equipo hablen el mismo idioma, facilita la lectura, reduce errores y hace que los proyectos sean más fáciles de mantener.

En este curso trabajamos con varias tecnologías: JavaScript, Node.js, Express, MongoDB/Mongoose, React y MySQL. Cada una utiliza convenciones de escritura que debemos respetar para evitar confusiones y asegurar que nuestro código sea profesional.

Esta guía recoge todas las normas esenciales que usaremos en el aula:

  • Cómo nombrar carpetas y archivos.
  • Cómo nombrar variables, constantes y funciones.
  • Cuándo usar mayúsculas y cuándo minúsculas.
  • Nomenclatura de objetos y modelos en Mongoose.
  • Nombres recomendados para tablas y columnas en MySQL.
  • Nombres de componentes, hooks y servicios en React.
  • Estructura recomendada para un backend y un frontend reales.

El objetivo es unificar criterios para que todos los alumnos desarrollen proyectos coherentes, ordenados y fáciles de entender. A partir de aquí, construiremos una tabla comparativa completa de todas las nomenclaturas del curso.

¿Por qué es importante una buena nomenclatura?

Una nomenclatura adecuada no solo mejora la legibilidad del código, sino que también facilita la colaboración entre desarrolladores. Cuando todos siguen las mismas reglas para nombrar variables, funciones y archivos, se reduce la curva de aprendizaje para nuevos miembros del equipo y se minimizan los errores causados por malentendidos.

Además, una buena nomenclatura contribuye a la mantenibilidad del código. Proyectos bien nombrados son más fáciles de actualizar y escalar, ya que los desarrolladores pueden entender rápidamente la estructura y el propósito de cada componente.

En resumen, invertir tiempo en definir y seguir una nomenclatura clara y consistente es fundamental para el éxito de cualquier proyecto de desarrollo web.

Nomenclatura para carpetas y archivos

En nuestros proyectos usaremos principalmente el estilo kebab-case para archivos y, en muchos casos, para nombres de utilidades y servicios.

  • Todo en minúsculas.
  • Palabras separadas con guiones (-).
  • Sin espacios, sin mayúsculas y sin guiones bajos.

Ejemplos recomendados:

  • productos.routes.js
  • usuarios.controller.js
  • configuracion-api.js
  • controllers/, models/, routes/

Para profundizar, consulta la sección ¿Qué es kebab-case?, donde verás más ejemplos de nombres correctos e incorrectos.

Nomenclatura para objetos (datos)

Llamamos objeto a los datos concretos que manejamos en el código (lo que guardamos en la base de datos, lo que recibimos por req.body, etc.).

  • Usamos camelCase para los nombres de objetos.
  • Empiezan en minúscula.
  • Su nombre debe describir qué representa el dato.
Correcto Incorrecto
const usuario = { nombre: "Ana" } const Usuario = { nombre: "Ana" }
const pedido = new Pedido() const Pedido = new Pedido()

Regla clave: si es un dato concreto (un usuario, un pedido, un producto), empieza siempre por minúscula.

Nomenclatura para modelos en Mongoose

En Mongoose distinguimos claramente entre esquema, modelo y documentos.

  • El esquema suele nombrarse en camelCase: productoSchema.
  • El modelo se nombra en PascalCase y en singular: Producto, Pedido, Usuario.
  • Los documentos (instancias) se guardan en variables en camelCase: const producto = new Producto(...). 
const productoSchema = new mongoose.Schema({
  nombre: String,
  precio: Number
});

// Modelo (clase / tipo)
const Producto = mongoose.model("Producto", productoSchema);

// Documento (objeto / dato concreto)
const producto = new Producto({
  nombre: "Camiseta React",
  precio: 19.99
});

Idea clave: el modelo (Producto) sirve para crear productos; la variable (producto) es un producto concreto.

Nomenclatura en MySQL / MariaDB

En bases de datos relacionales usaremos el estilo snake_case:

  • Tablas en plural: usuarios, productos, detalle_pedidos.
  • Columnas con nombres claros: usuario_id, precio_total, creado_en.
  • Clave primaria corta y coherente: id o usuario_id, pero siempre igual en todo el proyecto.
CREATE TABLE usuarios (
  id INT AUTO_INCREMENT PRIMARY KEY,
  nombre VARCHAR(100) NOT NULL,
  email VARCHAR(255) NOT NULL UNIQUE,
  creado_en DATETIME DEFAULT CURRENT_TIMESTAMP
);

CREATE TABLE pedidos (
  id INT AUTO_INCREMENT PRIMARY KEY,
  usuario_id INT NOT NULL,
  total DECIMAL(10,2) NOT NULL,
  estado ENUM('pendiente','completado','cancelado') DEFAULT 'pendiente',
  creado_en DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);

Nomenclatura en React

React organiza el código mediante componentes, que son piezas reutilizables de interfaz, y mediante páginas cuando usamos un sistema de rutas (React Router). Cada elemento tiene su propia convención de nombres para mantener un código limpio y profesional.

1) Componentes en React

Los componentes representan elementos visuales reutilizables. Siempre se nombran en PascalCase (mayúscula inicial y cada palabra también).

  • Navbar
  • ProductoCard
  • ProductosList
  • BotonPrimario

❌ Incorrecto:

  • navbar
  • producto-card
  • productos_list
function ProductoCard({ producto }) {
  return <article>{producto.nombre}</article>;
}

export default ProductoCard;

2) Hooks personalizados

Los hooks son funciones que comienzan SIEMPRE por use y que encapsulan lógica reutilizable.

Correcto:

  • useProductos()
  • useAuth()
  • useFormulario()

Incorrecto:

  • getProductos()
  • productosHook()
function useProductos() {
  const [productos, setProductos] = useState([]);

  useEffect(() => {
    fetch("/api/productos")
      .then(res => res.json())
      .then(data => setProductos(data));
  }, []);

  return { productos, setProductos };
}

export default useProductos;

3) Páginas en React (cuando usamos React Router)

Una página en React es un componente que representa una vista completa asociada a una ruta. Se guarda en src/pages/ y se nombra usando PascalCase terminado en Page.

Correcto:

  • HomePage.jsx
  • ProductosPage.jsx
  • LoginPage.jsx
  • DashboardPage.jsx

Incorrecto:

  • home.jsx
  • productos-page.js
  • PaginaProductos.jsx
// src/pages/ProductosPage.jsx
function ProductosPage() {
  return (
    <main>
      <h1>Listado de productos</h1>
    </main>
  );
}

export default ProductosPage;

4) Servicios / API en React

Las funciones que hacen peticiones al backend se guardan en src/services/ y se nombran en kebab-case o camelCase según el archivo.

Archivos recomendados:

  • productos.service.js
  • auth.service.js

Funciones dentro del archivo (camelCase):

  • obtenerProductos()
  • loginUsuario()
// src/services/productos.service.js
export async function obtenerProductos() {
  const res = await fetch("http://localhost:3000/api/productos");
  return res.json();
}

5) Estilos en React

Si usas CSS , los archivos suelen ir en minúsculas:

  • app.css
  • productos-page.css

6) Estructura recomendada de un proyecto React

src/
  components/
    Navbar.jsx
    ProductoCard.jsx
    BotonPrimario.jsx

  pages/
    HomePage.jsx
    ProductosPage.jsx
    LoginPage.jsx

  hooks/
    useProductos.js
    useAuth.js

  services/
    productos.service.js
    auth.service.js

  styles/
    variables.css
    global.css

  App.jsx
  main.jsx

Regla clave en React:
Componentes y páginas → PascalCase
Hooks → empiezan por use
Servicios y archivos → kebab-case o camelCase según tipo

Estructura de un proyecto MVC (Node + Express)

En este curso organizaremos el backend siguiendo el patrón MVC:

  • M de Modelo: la capa que habla con la base de datos.
  • V de Vista: lo que ve el usuario (HTML, React, plantillas...).
  • C de Controlador: la lógica que conecta modelos y vistas.

En proyectos con API + React, el backend se encarga de Modelos y Controladores, y el frontend React actúa como Vista.

1) Estructura básica de carpetas (backend)

Ejemplo de proyecto Node + Express organizado en MVC:

backend/
  src/
    config/
      db.js               # configuración de la base de datos
      env.js              # lectura de variables de entorno

    models/
      producto.model.js   # modelo Producto (Mongoose / Sequelize / etc.)
      pedido.model.js
      usuario.model.js

    controllers/
      productos.controller.js
      pedidos.controller.js
      usuarios.controller.js

    routes/
      productos.routes.js
      pedidos.routes.js
      usuarios.routes.js

    middlewares/
      auth.middleware.js
      error.middleware.js

    utils/
      formatear-fecha.js
      calcular-total.js

    app.js                 # configuración de la app Express
    server.js              # arranque del servidor

  public/                  # archivos estáticos (imágenes, CSS, JS)
  package.json
  .env

2) Relación entre carpetas y el patrón MVC

  • models/ → Modelo (M). Aquí definimos los esquemas y modelos que hablan con la base de datos.
    Ejemplos: Producto, Pedido, Usuario.
  • controllers/ → Controlador (C). Aquí va la lógica de cada recurso: qué pasa cuando se llama a GET /api/productos o POST /api/pedidos.
  • routes/ → Enrutador. No forma parte estricta de MVC clásico, pero en Express usamos rutas para conectar las URLs con los controladores.
  • views/ (cuando existe) → Vista (V). Si usamos plantillas HTML (EJS, Handlebars...) aquí irían las vistas. En nuestro curso, muchas veces la vista será la aplicación React.

3) Nomenclatura en un proyecto MVC

Aplicamos las mismas reglas de nombres que en el resto del manual:

  • Carpetas: models/, controllers/, routes/, middlewares/ (minúsculas, plural).
  • Archivos de modelos: producto.model.js, pedido.model.js (kebab-case + .model.js).
  • Archivos de controladores: productos.controller.js, pedidos.controller.js.
  • Archivos de rutas: productos.routes.js, usuarios.routes.js.
  • Modelos Mongoose en código: Producto, Pedido (PascalCase, singular).

Idea clave del MVC:
Cada carpeta tiene una responsabilidad clara.
Esto hace que el proyecto sea más fácil de entender, mantener y ampliar.

¿Qué es kebab-case?

El estilo kebab-case es una convención muy usada para nombrar archivos y carpetas en desarrollo web. Se caracteriza por:

  • Usar solo minúsculas.
  • Separar palabras con guiones (-).
  • No usar espacios, guiones bajos ni mayúsculas.
Correcto (kebab-case) Incorrecto
productos.routes.js ProductosRoutes.js
usuarios.controller.js usuarios_Controller.js
validar-datos.js validarDatos.js

Regla rápida:
Usa kebab-case siempre para archivos y carpetas, excepto cuando nombres modelos, clases o componentes (que usan PascalCase).
