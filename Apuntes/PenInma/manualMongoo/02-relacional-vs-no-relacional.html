Base de datos relacional vs no relacional

Comparativa práctica y sencilla: qué es cada una, cuándo conviene y cómo traducir conceptos entre MongoDB y MySQL.

🏠 Inicio ⬅ Tema anterior Siguiente tema ➜

🏗️ Base de datos RELACIONAL (SQL)

Organiza datos en tablas (filas/columnas) con relaciones mediante claves.

Ejemplo mínimo (SQL)

CREATE TABLE usuarios (
  id INT PRIMARY KEY AUTO_INCREMENT,
  nombre VARCHAR(100) NOT NULL,
  email VARCHAR(100) UNIQUE
);
CREATE TABLE posts (
  id INT PRIMARY KEY AUTO_INCREMENT,
  titulo VARCHAR(200),
  usuario_id INT,
  FOREIGN KEY (usuario_id) REFERENCES usuarios(id)
);
  • Esquema rígido tipos y columnas definidos
  • JOINs relaciones complejas, reporting potente
  • ACID transacciones multi-tabla seguras

🗂️ Base de datos NO RELACIONAL (NoSQL)

Almacena datos como documentos (JSON) en colecciones, con estructura flexible.

Ejemplo mínimo (MongoDB)

// Documento en "usuarios"
{
  "_id": "507f1f77bcf86cd799439011",
  "nombre": "Ana García",
  "posts": [{ "titulo": "Mi primer post" }],
  "perfil": { "edad": 25, "ciudad": "Madrid" }
}
  • Esquema flexible documentos pueden variar
  • Embed/Reference subdocumentos o ids
  • Escala horizontal pensado para repartir carga

⚖️ Comparación directa

Aspecto Relacional (SQL) No relacional (NoSQL)
Estructura Tablas Documentos / colecciones
Esquema Rígido (tipos fijos) Flexible (campos opcionales)
Relaciones JOINs + claves foráneas Embebidos o referencias
Lenguaje SQL (SELECT/INSERT/…) API/operadores (find, aggregate)
Escalabilidad Vertical + réplicas lectura Horizontal (sharding) nativo
Consistencia ACID por defecto Eventual por diseño (configurable)

🧭 ¿Cuándo usar cada una?

Relacional (SQL)

  • Reporting con muchos cruces
  • Transacciones críticas
  • Esquema estable

Ejemplos: banca, ERP, inventarios.

No relacional (NoSQL)

  • Entidad con subpartes naturales (perfil, pedido)
  • Esquema cambiante / MVP
  • Alto volumen y baja latencia

Ejemplos: redes sociales, catálogos, IoT.
