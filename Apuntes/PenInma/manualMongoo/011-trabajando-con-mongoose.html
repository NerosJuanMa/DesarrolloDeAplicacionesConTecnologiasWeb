🔗 Empezamos a trabajar en nuestro CRUD

En la Lección 10 definimos el Schema y creamos el Model que conecta con la colección productos. Aquí, el controlador utiliza ese modelo para implementar el CRUD completo.

Recordatorio (Lección 10): 
// src/models/Producto.js
import mongoose from 'mongoose';

// Definimos el esquema
const productoSchema = new mongoose.Schema({
  nombre: { type: String, required: true, trim: true }, // índice simple
  precio: { type: Number, required: true, min: 0 },
  stock:  { type: Number, default: 0, min: 0 },
  activo: { type: Boolean, default: true },
  imagen: { type: String }
}, { timestamps: true });



// Creamos el modelo
const Producto = mongoose.model('Producto', productoSchema);

export default Producto;

🧠 Cómo se relacionan

  • Schema: define qué campos existen y cómo (tipo, required, min, default, trim…)
  • Model: expone métodos como .create(), .find(), .findById(), .findByIdAndUpdate(), .findByIdAndDelete()
  • Controlador: recibe la petición HTTP, llama al Model y devuelve la respuesta JSON (con códigos HTTP correctos)
Cadena completa: HTTP → Controlador → Modelo (valida con Schema) → MongoDB → Modelo → Controlador → JSON

🧱 Requisitos previos

  • Conexión a MongoDB operativa (connectDB()) con MONGO_URI y MONGODB_DB en .env
  • Middleware de JSON en Express: app.use(express.json())
  • Modelo Producto funcionando (ver arriba)
  • Rutas montadas en /api/productos

🔗 Del Esquema/Modelo (Lección 10) al Controlador (Lección 11)

¿Por qué el CRUD se implementa en el Controller?

En una API con Express + Mongoose seguimos una separación de responsabilidades (similar a MVC). Ahora vamos a trabajar en el archivo controlador que es el que se comunica con los datos a través del modelo.

Capa Qué hace Ejemplo en nuestro proyecto
Rutas Reciben la URL y delegan en el controlador. src/routes/productos.routes.js → r.post('/', ctrl.crearProducto)
Controller Orquesta el flujo de la petición: valida lo básico, invoca al modelo y construye la respuesta HTTP (códigos, JSON). src/controllers/productosController.js (lo que implementamos aquí)
Modelo Define el Schema (tipos y reglas) y expone métodos de acceso a datos. src/models/Producto.js → Producto.create/find/findById...
Beneficios: código más limpio y mantenible, validaciones consistentes (el Schema se aplica siempre), respuestas HTTP correctas (201, 400, 404, 409, 500), y facilidad para testear cada capa por separado.

📂 Dónde vamos a editar

  • src/controllers/productosController.js — aquí escribirás los métodos del CRUD (Create, Read, Update, Delete).
  • src/routes/productos.routes.js — ya debería apuntar a cada método del controlador.
  • src/models/Producto.js — ya creado en la Lección 10; sus validaciones se aplican automáticamente.
Importante: el Controller no define la estructura de datos (eso es del Schema), ni gestiona la conexión (eso es de config/db.js). Su rol es coordinar: leer la petición, invocar al modelo y responder. 
// Flujo resumido
// Cliente → (HTTP) → Rutas → Controller → Modelo (valida con Schema) → MongoDB
//                                               ↓
//                                      Respuesta JSON + códigos HTTP

🛠️ CRUD paso a paso con Mongoose

1) Crear — POST /api/productos

Inserta un producto nuevo. Validamos lo mínimo (nombre y precio) y devolvemos el documento creado junto con la cabecera Location.

La cabecera location indica la URL del nuevo recurso creado.

// POST /api/productos - Crear
  async crearProducto(req, res) {
    try {
      const producto = await Producto.create(req.body);//validamos segun el esquema
      res.status(201).json({ status: 'ok', data: producto });
    } catch (error) {
      console.error(error);
      res.status(400).json({ status: 'error', message: error.message });
    }
  }

res.status(201)
   .location(`/api/productos/${doc._id}`)
   .json({ status: 'ok', data: doc });

🧱 Paso a paso

Parte del código Qué hace Por qué se usa
res.status(201) Devuelve el código HTTP 201 Created. Indica que el servidor ha creado un nuevo recurso correctamente.
.location(`/api/productos/${doc._id}`) Añade una cabecera HTTP Location con la ruta del nuevo producto. Permite al cliente saber dónde acceder al recurso recién creado.
.json({ status: 'ok', data: doc }) Envía al cliente el documento completo creado en formato JSON. Permite mostrar o reutilizar los datos inmediatamente en el frontend.

📘 Ejemplo completo del controlador


    import Producto from '../models/Producto.js'; // ← importa el modelo
    
    async crearProducto(req, res) {
  try {
    const doc = await Producto.create(req.body);
    res.status(201)
       .location(`/api/productos/${doc._id}`)
       .json({ status: 'ok', data: doc });
  } catch (error) {
    res.status(500).json({ status: 'error', mensaje: 'Error al crear el producto' });
  }
}

🔍 Qué envía el servidor al cliente

Content-Type: application/json

{
  "status": "ok",
  "data": {

✅ En resumen:
  • 201 Created → el recurso se creó correctamente.
  • Location → indica dónde se encuentra el nuevo recurso.
  • JSON → devuelve los datos recién creados.

De esta forma tu API sigue las buenas prácticas REST y cualquier cliente sabrá cómo interactuar con tus recursos.

🧠 Explicación técnica

  • doc → es el documento recién creado en MongoDB (objeto Mongoose).
  • doc._id → el identificador único generado automáticamente por MongoDB.
  • Location → parte del estándar HTTP 1.1 (RFC 7231) para respuestas 201.
💬 Truco didáctico: Piensa que el servidor dice literalmente:
“✅ He creado tu producto y lo guardé en la base de datos.
🗂️ Puedes encontrarlo ahora en /api/productos/ID.”
💡 Curiosidad: Esta estructura es la misma que usan las APIs profesionales (por ejemplo, GitHub o Stripe) para indicar al cliente la dirección exacta de un nuevo recurso.

🧪 ¿Cuándo se validan los datos en Mongoose?

Cuando usamos Mongoose, definimos un Schema con tipos y reglas (required, min, maxlength, enum, etc.). Pero… ¿cuándo se comprueban realmente esas reglas? La validación ocurre automáticamente dentro del modelo, en el momento en que intentas guardar o crear un documento.

Idea clave: Tú no llamas a ninguna función validate() manualmente. Mongoose valida los datos automáticamente cuando usas métodos como create() o save().

1️⃣ Ejemplo básico: Producto.create()

Imagina este esquema:

// 📄 src/models/Producto.js
const productoSchema = new mongoose.Schema({
  nombre: { type: String, required: true, trim: true, index: true },
  precio: { type: Number, required: true, min: 0 },
  stock:  { type: Number, default: 0, min: 0 },
  activo: { type: Boolean, default: true },
  imagen: { type: String }
}, { timestamps: true });

const Producto = mongoose.model("Producto", productoSchema);

Y este controlador:

// POST /api/productos - Crear
async function crearProducto(req, res) {
  try {
    const producto = await Producto.create(req.body);
    res.status(201).json({ status: "ok", data: producto });
  } catch (error) {
    console.error(error);
    res.status(400).json({ status: "error", message: error.message });
  }
}

Cuando llamas a Producto.create(req.body), Mongoose hace internamente dos pasos: 

const doc = new Producto(req.body);  // 1️⃣ Aplica el Schema y valida
await doc.save();                    // 2️⃣ Si todo está bien, guarda en MongoDB
  • Si los datos cumplen el Schema → el documento se guarda.
  • Si los datos NO cumplen el Schema → lanza un ValidationError y entra en el catch.
Ejemplo de error: Si el precio es negativo o falta el nombre, Mongoose no guarda nada y lanza un error de validación.

2️⃣ ¿Qué comprueba exactamente la validación?

Mongoose revisa los datos que llegan en req.body y los compara con el Schema:

  • ¿Está el campo nombre si es required: true?
  • ¿Es precio un número? ¿Es mayor o igual que 0 (min: 0)?
  • ¿Es stock un número? ¿Es mayor o igual que 0?
  • ¿Coinciden los tipos (String, Number, Boolean...)?
  • ¿Se cumplen otras reglas como enum, maxlength, etc.?

Si alguna regla falla, Mongoose recoge todos los fallos y los lanza como un ValidationError, que tú capturas en el catch y devuelves al cliente.

3️⃣ ¿Qué pasa con new Producto() y save()?

Otra forma de crear documentos es esta: 

const producto = new Producto(req.body);  // Aquí ya se aplica el Schema
await producto.save();                    // Aquí se dispara la validación y el guardado

La idea es la misma: al guardar (save) es cuando Mongoose valida según el Schema.

Qué debes recordar:
  • El Schema NO almacena datos, define reglas y estructura.
  • El Modelo (Producto) aplica esas reglas cuando creas o guardas.
  • La validación pasa siempre antes de que los datos lleguen a MongoDB.

4️⃣ ¿Y al actualizar? runValidators: true

Con operaciones de actualización como findByIdAndUpdate() o updateOne(), por defecto Mongoose no valida todos los campos.

Si quieres que también se apliquen las reglas del Schema al actualizar, debes activar la opción runValidators: 

// PUT /api/productos/:id - Actualizar con validación
async function actualizarProducto(req, res) {
  try {
    const productoActualizado = await Producto.findByIdAndUpdate(
      req.params.id,
      req.body,
      {
        new: true,          // devuelve el documento ya actualizado
        runValidators: true // ✅ aplica validaciones del Schema al actualizar
      }
    );

    if (!productoActualizado) {
      return res.status(404).json({ status: "error", message: "Producto no encontrado" });
    }

    res.json({ status: "ok", data: productoActualizado });
  } catch (error) {
    console.error(error);
    res.status(400).json({ status: "error", message: error.message });
  }
}

De esta forma, si alguien intenta poner un precio negativo o borrar un campo obligatorio en una actualización, Mongoose volverá a lanzar un ValidationError.

Resumen de validación:
  • Definimos las reglas en el Schema.
  • El Modelo aplica esas reglas al crear o guardar documentos.
  • create() y save() siempre validan.

👀 READ — Leer productos desde MongoDB (paso a paso)

En esta parte del CRUD aprenderás a leer datos con Mongoose. Lo haremos en 3 pasos:

  1. Leer todos los productos
  2. Leer uno por su _id
  3. Leer con filtros, orden y paginación
Requisitos previos:
  • Modelo Producto en src/models/Producto.js
  • Router montado en src/app.js con app.use('/api/productos', productosRoutes)
  • express.json() cargado para recibir JSON

A) Leer todos — GET /api/productos

Devuelve todos los documentos de la colección productos.

// 📄 src/controllers/productosController.js
async listarProductos(req, res) {

  } catch (error) {
    console.error(error);

B) Leer uno por ID — GET /api/productos/:id

Cuando conoces el _id puedes pedir solo ese documento.


  // GET /api/productos/:id - Obtener un producto por su ID
async obtenerProducto(req, res) {
  try {

    // 1️⃣ Extraemos el ID que llega por la URL (ruta dinámica: /api/productos/:id)
    //    Ejemplo de URL: /api/productos/67abc1230d91f89c3a7e1021
    //    req.params.id contiene ese valor.
    const producto = await Producto.findById(req.params.id);

    // 2️⃣ Si no existe un documento con ese ID → devolvemos 404 (no encontrado)
    if (!producto) {
      return res.status(404).json({
        status: 'error',
        message: 'Producto no encontrado'
      });
    }

    // 3️⃣ Si todo va bien → enviamos el producto encontrado
    res.json({
      status: 'ok',
      data: producto
    });

  } catch (error) {

    // 4️⃣ Errores inesperados (por ejemplo un ID mal formado: "1234" en vez de un ObjectId)
    console.error(error);

    res.status(500).json({
      status: 'error',
      message: 'Error al obtener producto'
    });
  }
}
Ruta correspondiente: 
// 📄 src/routes/productos.routes.js
route.get('/:id', productosController.obtenerProducto);

4) Actualizar documentos — PUT vs PATCH

En Mongoose podemos actualizar un producto de dos formas: reemplazando todo el documento (PUT) o modificando únicamente algunos campos (PATCH). Ambos métodos utilizan findByIdAndUpdate() pero su intención es diferente.

Idea clave: PUT = sustitución completa. PATCH = modificación parcial.

🔄 PUT — Actualización completa con /api/productos/:id

Se usa cuando quieres reemplazar todo el documento. El cliente debe enviar todos los campos del producto, aunque solo uno cambie. 

// PUT /api/productos/:id - Reemplazar producto completo
async reemplazarProducto(req, res) {
  try {
    const producto = await Producto.findByIdAndUpdate(
      req.params.id,
      req.body,
      {
        new: true,          // devuelve el documento actualizado
        runValidators: true // 🔒 valida según el Schema
      }
    );

    if (!producto) {
      return res.status(404).json({ status: 'error', message: 'Producto no encontrado' });
    }

    res.json({ status: 'ok', data: producto });
  } catch (error) {
    console.error(error);
    res.status(400).json({ status: 'error', message: error.message });
  }
}
¿Cuándo usar PUT?
  • Cuando quieres enviar toda la representación del recurso.
  • Cuando la lógica de la API obliga a enviar el producto completo.
  • Cuando quieres asegurarte de que no quedan campos "viejos" o no enviados.

🛠 PATCH — Actualización parcial con /api/productos/:id

Se usa cuando solo quieres modificar campos concretos. No hace falta enviar todos los atributos del producto. 

// PATCH /api/productos/:id - Actualizar parcialmente
async actualizarProducto(req, res) {
  try {
    const producto = await Producto.findByIdAndUpdate(
      req.params.id,
      req.body,
      {
        new: true,          // devuelve el documento actualizado
        runValidators: true // 🔒 aplica reglas del Schema también en PATCH
      }
    );

    if (!producto) {
      return res.status(404).json({ status: 'error', message: 'Producto no encontrado' });
    }

    res.json({ status: 'ok', data: producto });
  } catch (error) {
    console.error(error);
    res.status(400).json({ status: 'error', message: error.message });
  }
}
¿Cuándo usar PATCH?
  • Cuando solo quieres cambiar uno o varios campos.
  • Cuando la app hace ediciones rápidas (cambiar precio, stock, estado...)
  • Cuando quieres minimizar datos enviados por el cliente.

🧪 ¿Qué hace realmente runValidators: true?

Por defecto, Mongoose no valida los datos en métodos de actualización como findByIdAndUpdate(). Eso significa que podrías enviar un precio negativo o borrar un campo obligatorio sin que Mongoose lo impida.

⚠️ Problema: Sin validación, PATCH y PUT podrían romper el modelo.

Para evitarlo, usamos: 

runValidators: true

Esto obliga a Mongoose a comprobar las reglas del Schema:

  • required
  • min y max
  • minlength / maxlength
  • enum
  • match (regex)
Resultado: Cualquier actualización que viole el Schema será rechazada automáticamente.

📌 Resumen final para alumnos

  • PUT reemplaza todo el documento.
  • PATCH modifica solo lo que envíes.
  • Ambos usan findByIdAndUpdate().
  • runValidators: true garantiza que las reglas del Schema se mantengan.

5) Eliminar documentos — DELETE /api/productos/:id

El método DELETE se utiliza para eliminar un documento existente en la colección. En este caso, eliminamos un producto usando su identificador único _id.

Idea clave: DELETE elimina el recurso por completo. Pero en proyectos profesionales se suele preferir el borrado lógico, donde el documento no desaparece, solo se marca como inactivo.

🗑️ DELETE — Eliminar un producto físicamente

Este método busca el producto por su _id y lo elimina de la base de datos. Si el producto no existe, respondemos con un error 404. 

// DELETE /api/productos/:id - Eliminar
  async eliminarProducto(req, res) {
    try {
      const producto = await Producto.findByIdAndDelete(req.params.id);
      if (!producto) {
        return res.status(404).json({ status: 'error', message: 'Producto no encontrado' });
      }
      res.status(204).send();
    } catch (error) {
      console.error(error);
      res.status(500).json({ status: 'error', message: 'Error al eliminar producto' });
    }
  }
}
Ruta correspondiente: 
// 📄 src/routes/productos.routes.js
¿Por qué usamos 204 No Content?
  • Indica que la operación se completó correctamente.
  • No se devuelve cuerpo JSON porque el recurso ya no existe.
  • Es la práctica recomendada en APIs REST.

🟧 Alternativa profesional: Borrado lógico

En muchos proyectos no interesa eliminar productos definitivamente (por auditoría, informes, histórico, etc.). En esos casos, en lugar de borrar el documento se marca como inactivo: 

// Borrado lógico: actualizar "activo" a false
await Producto.findByIdAndUpdate(id, { activo: false }, { new: true });

Y luego en el listado se muestran solo los productos activos: 

// Listar solo activos
Producto.find({ activo: true });
Cuándo usar borrado lógico:
  • Cuando necesitas conservar histórico de datos.
  • Cuando no puedes perder el registro del producto.
  • Cuando hay relaciones con pedidos, usuarios u otras colecciones.

📌 Resumen final para alumnos

  • DELETE elimina el documento completamente.
  • Si el _id no existe → se devuelve 404.
  • 204 No Content confirma que el borrado fue correcto.
  • En proyectos reales, se usa mucho el borrado lógico con activo:false.
