🧩 Guía de nomenclatura en proyectos Node.js + Express + Mongoose

Una buena organización y nombres coherentes son esenciales para que un proyecto sea fácil de entender, mantener y escalar. En programación, llamamos a esto nomenclatura o naming convention.

💡 Regla general: Los archivos y carpetas se escriben en minúsculas y con guiones o puntos para separar palabras. Las clases y funciones siguen convenciones específicas que veremos a continuación.

📦 backend-mongoose/

✅ Ventaja: Con esta estructura y nomenclatura uniforme, cualquier desarrollador o alumno puede identificar de un vistazo:

  • 📂 controllers/ → Lógica de negocio (qué hace la aplicación).
  • 📂 routes/ → Endpoints que conectan URLs con funciones.
  • 📂 models/ → Estructura de los datos en MongoDB (Mongoose).
  • 📂 config/ → Configuración general (base de datos, entorno, etc.).

🧠 Ejemplo práctico de coherencia

📄 Archivo: controllers/productos.controller.js

class ProductosController {
  async listarProductos(req, res) {
    res.json({ ok: true, mensaje: 'Listado de productos' });
  }

  async crearProducto(req, res) {
    res.status(201).json({ ok: true, mensaje: 'Producto creado' });
  }
}

export default new ProductosController();

📄 Archivo: routes/productos.routes.js

import { Router } from 'express';
import productosController from '../controllers/productos.controller.js';

const route = Router();

route.get('/', productosController.listarProductos);
route.post('/', productosController.crearProducto);

export default route;
⚠️ Atención: Asegúrate de que los nombres de las funciones en las rutas coincidan exactamente con los del controlador. Si en el controlador defines listarProductos(), no la llames obtenerProductos() en las rutas.
💬 Consejo profesional: Usa siempre nombres autoexplicativos (que digan qué hacen). Por ejemplo:
  • ✅ actualizarProducto() → se entiende al leerlo.
  • ❌ modificar() → demasiado genérico, confuso.

🎯 Objetivo: Un código bien nombrado no necesita comentarios para entenderse. Si todos los archivos siguen la misma convención, el proyecto será más profesional, más limpio y mucho más fácil de enseñar y mantener.

🧱 1️⃣ Estructura inicial del proyecto con Mongoose

Antes de empezar a crear esquemas y modelos, debemos preparar un proyecto Node.js bien organizado. Esta estructura es la base de cualquier aplicación profesional que use MongoDB con Mongoose.

📁 Paso 1. Crear el proyecto y carpeta principal

Verificamos la versión de Node.js instalada (mínimo v14+): 
node -v
Luego, creamos la carpeta del proyecto e inicializamos npm: 
mkdir backend-mongoose (crea la carpeta del proyecto)
cd backend-mongoose (entra en la carpeta)
npm init -y (inicializa npm con nuestro package.json)

Esto genera tu archivo package.json. Edita la propiedad "type" para trabajar con módulos ES:

{
  "name": "backend-mongoose",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    
  }
}
💡 Consejo: Definir "type": "module" te permite usar import / export en lugar de require.

⚙️ Paso 2. Instalar dependencias básicas

Una vez creado el proyecto con npm init -y, vamos a instalar las librerías que harán posible conectarnos con MongoDB y crear nuestro servidor.

📦 Dependencias esenciales

npm install express mongoose dotenv cors

Además, instalamos nodemon como dependencia de desarrollo (para reiniciar el servidor automáticamente cada vez que guardamos un cambio): 

npm install --save-dev nodemon

🔍 ¿Qué hace cada paquete?

  • express: crea el servidor web y las rutas de nuestra API.
  • mongoose: nos permite conectar y trabajar con MongoDB desde Node.js de forma más sencilla y estructurada (usando esquemas y modelos).
  • dotenv: gestiona variables de entorno (credenciales, puertos, URL del cluster, etc.) sin que aparezcan en el código.
  • cors: permite que el backend acepte peticiones desde un frontend (por ejemplo, React o HTML local).
  • nodemon: reinicia el servidor al detectar cambios, para no tener que pararlo y arrancarlo a mano cada vez.

🧭 Configurar scripts en package.json

Consejo: puedes instalar todas las librerías en una sola línea para ahorrar tiempo, o una por una si quieres observar cómo se añaden al package.json. En ambos casos el resultado es idéntico. 
npm install express mongoose dotenv cors  
npm install --save-dev nodemon

Así quedará tu package.json:

{
  "name": "backend-mongoose",
  "version": "1.0.0",
  "type": "module",
  "scripts": {
    "start": "node src/server.js",
    "dev": "nodemon src/server.js"
  },
  "dependencies": {
    "cors": "^2.8.5",
    "dotenv": "^16.0.3",
    "express": "^4.18.2",
    "mongoose": "^7.3.1"
  },
  "devDependencies": {
    "nodemon": "^2.0.22"
  }
}
✅ Ventaja: los scripts "start" y "dev" nos permiten arrancar el servidor fácilmente en modo producción o desarrollo.

🏗️ Paso 3. Crear estructura de carpetas (patrón MVC)

Vamos a organizar el proyecto para que el código sea mantenible, testable y fácilmente ampliable. Usaremos una distribución inspirada en MVC (Modelo–Vista–Controlador) para separar responsabilidades.

¿Qué es MVC? El modelo MVC es un patrón de diseño que separa la lógica de la aplicación en tres componentes principales:

1. Modelo (M): maneja los datos y la lógica de negocio (en nuestro caso, los esquemas y modelos de Mongoose). 2. Vista (V): representa la interfaz de usuario (en una API REST, esto se traduce en las respuestas JSON). 3. Controlador (C): recibe las solicitudes del usuario, interactúa con el modelo y devuelve la vista adecuada (en nuestro caso, los controladores que gestionan las rutas).

En nuestro proyecto, la estructura de carpetas quedará así:

backend-mongoose/
├─ .env
├─ .gitignore
├─ package.json
├─ src/
│  ├─ server.js            ← archivo de entrada (o app.js)
│  ├─ config/              ← configuración de la app
│  │  ├─ db.js             ← conexión a MongoDB con Mongoose
│  │  
│  ├─ models/              ← esquemas y modelos de datos (Mongoose)
│  │  └─ Producto.js
│  ├─ controllers/         ← lógica de negocio por recurs
│  │  └─ productos.controller.js
│  ├─ routes/              ← endpoints Express que llaman a controladores
│  │  └─ productos.routes.js
│     
└─ README.md

📍 src/server.js (o app.js)

Es el punto de entrada de la aplicación. Crea la instancia de Express, aplica middlewares (p. ej., express.json() y cors()), monta las rutas y arranca el servidor en process.env.PORT. Suele requerir la conexión a la BD.

⚙️ src/config/

  • db.js: configura y realiza la conexión Mongoose usando MONGODB_URI y MONGODB_DB.
  • env.js: inicializa dotenv y expone las variables de entorno (centraliza process.env).

🧱 src/models/

Contiene los Schemas y Modelos de Mongoose. Cada archivo define la forma de los documentos, validaciones y métodos estáticos/de instancia. Ej.: Producto.js con campos nombre, precio, stock, etc.

🧠 src/controllers/

Implementa la lógica de negocio por recurso (productos, usuarios…). Recibe req/res, orquesta llamadas al modelo y devuelve respuestas. Mantiene el código de las rutas limpio y reutilizable.

🧭 src/routes/

Declara los endpoints (p. ej., GET /api/productos, POST /api/productos) y los conecta con su controlador correspondiente. No contiene negocio; solo mapea URLs → controladores.

🛠️ README.md

Archivo donde explica la estructura del proyecto, cómo configurarlo y ejecutarlo, así como detalles sobre las API disponibles.Puedes ir creándolo a la vez.

Archivos de raíz
  • .env: credenciales y configuración (no se sube a Git).
  • .gitignore: excluye node_modules, .env y artefactos temporales.
  • package.json: metadatos del proyecto y scripts (dev, start, etc.).

🧭 Mini introducción a MVC

MVC es un patrón de arquitectura que separa responsabilidades para facilitar el mantenimiento:

  • Modelo (M) → Datos y reglas de negocio en torno a la persistencia. En nuestro proyecto: src/models/ (Mongoose).
  • Vista (V) → Interfaz de usuario. En una API pura no hay “vistas” clásicas; el rol lo cumple el cliente (frontend) o las respuestas JSON.
  • Controlador (C) → Recibe la petición, aplica la lógica y devuelve la respuesta. En nuestro proyecto: src/controllers/, conectados por src/routes/.

¿Por qué es tan usado? Porque permite escalar el proyecto sin que el código se convierta en un “monolito” difícil de mantener. Separar rutas, controladores, modelos y configuración hace que cada capa sea testable, reutilizable y legible.

🖥️ Paso 4. Archivo server.js — Punto de entrada de la aplicación

El archivo server.js (también puede llamarse app.js) es el punto de entrada de nuestra aplicación Node.js. Aquí se configura el servidor Express, se cargan las variables de entorno y se define el puerto donde escuchará la API. 

import express from 'express';
import dotenv from 'dotenv';
import productosRoutes from './routes/productos.routes.js';//importamos las rutas de productos

// 🔹 Cargar variables del archivo .env
dotenv.config();

// 🔹 Crear instancia de la aplicación Express
const app = express();
app.use(express.json());

// ✅ Aquí decides la ruta base
app.use('/api/productos', productosRoutes);

// 🔹 Usar el puerto definido en .env o un valor por defecto
const PORT = process.env.PORT || 3000;

try {
  // 🔹 Iniciar el servidor
  app.listen(PORT, () => {
    console.log(`🚀 Servidor corriendo en http://localhost:${PORT}`);
  });
} catch (error) {
  console.error('❌ Error al iniciar el servidor:', error);
}

🔍 Explicación paso a paso

  • 1️⃣ Importación de dependencias: express es el framework que nos permite crear un servidor web rápido y modular. dotenv carga automáticamente las variables definidas en el archivo .env para que puedan usarse en el proyecto.
  • 2️⃣ Configuración de variables de entorno: La instrucción dotenv.config() busca un archivo .env en la raíz del proyecto y lo carga en process.env. Así podemos acceder a valores sensibles como el puerto o la URI de MongoDB sin escribirlos directamente en el código.
  • 3️⃣ Creación del servidor Express: const app = express(); inicializa la aplicación Express. Más adelante añadiremos aquí middlewares como express.json() o cors() y las rutas de nuestra API.
  • 4️⃣ Definición del puerto: const PORT = process.env.PORT || 3000; indica que, si existe una variable PORT en el archivo .env, se use esa; si no, se usará el puerto 3000 por defecto.
  • 5️⃣ Inicio del servidor: app.listen(PORT, ...) pone a escuchar al servidor en ese puerto. Si todo funciona, muestra en consola el mensaje Servidor corriendo en http://localhost:4000.
  • 6️⃣ Manejo de errores: El bloque try/catch captura posibles errores al iniciar el servidor (por ejemplo, si el puerto está ocupado o hay un problema de permisos).
📦 En resumen: este archivo es el “corazón” de tu backend. Su función es inicializar Express, cargar la configuración global y mantener en marcha el servidor para que las rutas puedan atender peticiones.
📘 Recuerda: ya aprendimos en el tema de Node.js que el archivo package.json puede incluir una sección llamada "scripts", donde definimos atajos de ejecución para comandos frecuentes. En nuestro caso, añadimos dos scripts muy útiles: 
"scripts": {
  "start": "node src/server.js",
  "dev": "nodemon src/server.js"
}
  • npm run start → ejecuta el servidor con Node.js (modo normal).
  • npm run dev → usa nodemon para reiniciar automáticamente el servidor cuando detecta cambios en los archivos (modo desarrollo).
Esto nos ahorra tiempo, evita reiniciar manualmente el servidor y mantiene un flujo de trabajo profesional.
💡 Prueba rápida: Ejecuta en la terminal npm run dev (si tienes nodemon) o node src/server.js. Si todo está correcto, verás en consola: 🚀 Servidor corriendo en http://localhost:3000

🧭 Paso 5. Crear el archivo de rutas productos.routes.js

En una API organizada con Express, las rutas son los caminos o direcciones que los usuarios pueden usar para pedir información o enviar datos. Cada ruta indica qué debe hacer el servidor cuando alguien accede a una URL concreta.

Por ejemplo:

  • GET /api/productos → devuelve la lista de productos.
  • POST /api/productos → añade un nuevo producto.
  • GET /api/productos/123 → busca un producto concreto por su ID.

📁 Ubicación y nombre del archivo

Crea una carpeta llamada routes dentro de src/, y dentro un archivo llamado productos.routes.js.

📜 Código base del archivo

import express from 'express';

// 🔹 Creamos un "enrutador" de Express
const route = express.Router();

// 🔹 Importamos el controlador (lógica de los productos)
import productosController from '../../controllers/productosController.js';

// 🔹 Definimos las rutas básicas del recurso "productos"
route.get('/');         // obtener todos los productos
route.post('/');        // crear un nuevo producto
route.get('/:id');      // obtener un producto por ID
route.put('/:id');      // actualizar un producto
route.delete('/:id');   // eliminar un producto

// 🔹 Exportamos el router para poder usarlo en el servidor
export default route;

🧩 Explicación paso a paso

  • 1️⃣ import express from 'express'; Importa Express para poder usar su sistema de rutas.
  • 2️⃣ const route = express.Router(); Crea un “mini-servidor” interno llamado Router que agrupa rutas relacionadas, en este caso todas las de productos.
  • 3️⃣ import productosController... Aquí importaremos más adelante el archivo con la lógica de negocio (lo que hace cada ruta).
  • 4️⃣ route.get(...), route.post(...), etc. Son los distintos métodos HTTP que usa una API:
    • GET → leer información.
    • POST → crear nuevos datos.
    • PUT → actualizar datos existentes.
    • DELETE → borrar datos.
  • 5️⃣ export default route; Permite que este grupo de rutas pueda ser usado por el archivo principal del servidor (server.js), que más adelante las “montará” en una dirección como /api/productos.
💡 Resumen: este archivo solo define los caminos (rutas) y qué tipo de acción se espera en cada uno. La lógica que se ejecuta (crear, leer, actualizar, borrar) se escribirá más adelante en el controlador.

🧭 Paso 6. Conectar las rutas en el servidor principal

En el paso anterior definimos las rutas básicas dentro de src/routes/productos.routes.js, pero aún no las hemos conectado con nuestro servidor. Ahora iremos al archivo principal server.js (o app.js) para montar la ruta base del recurso.

📁 Ubicación del archivo

src/
├─ config/
│  └─ db.js
├─ controllers/
│  └─ productos.controller.js
├─ models/
│  └─ Producto.js
├─ routes/
│  └─ productos.routes.js
└─ server.js   ← aquí creamos la ruta base

⚙️ Código de server.js

Importamos Express, la conexión a la base de datos y el archivo de rutas. Luego usamos el método app.use() para indicar que todas las rutas de productos estarán bajo el prefijo /api/productos esta es la ruta que hemos definido en el servidor. 

import express from 'express';
import dotenv from 'dotenv';
import productosRoutes from './routes/productos.routes.js';//importamos las rutas de productos

// 🔹 Cargar variables del archivo .env
dotenv.config();

// 🔹 Crear instancia de la aplicación Express
const app = express();
app.use(express.json());

// ✅ Aquí decides la ruta base
app.use('/api/productos', productosRoutes);

// 🔹 Usar el puerto definido en .env o un valor por defecto
const PORT = process.env.PORT || 3000;

try {
  // 🔹 Iniciar el servidor
  app.listen(PORT, () => {
    console.log(`🚀 Servidor corriendo en http://localhost:${PORT}`);
  });
} catch (error) {
  console.error('❌ Error al iniciar el servidor:', error);
}
💡 Ruta base: el prefijo /api/productos actúa como el “camino principal” del recurso. Todo lo que definiste en productos.routes.js (por ejemplo GET '/' o POST '/') ahora funcionará como:
  • GET /api/productos → obtener todos los productos
  • POST /api/productos → crear un nuevo producto
  • GET /api/productos/:id → obtener por ID
  • PUT /api/productos/:id → actualizar
  • DELETE /api/productos/:id → eliminar
✅ Comprueba: si el servidor muestra el mensaje. Arranca con npm run dev. 🚀 Servidor corriendo en http://localhost:3000, ya tienes tu API lista para recibir peticiones.

🧠 BONUS — Cómo ver quién está usando un puerto y cerrar la conexión

A veces, cuando intentas arrancar el servidor, aparece un error como: 

Error: listen EADDRINUSE: address already in use :::3000

Esto significa que **otro proceso ya está usando el mismo puerto** (por ejemplo, un servidor anterior que no se cerró correctamente).

💻 En Windows (PowerShell o CMD)

  1. Ver quién usa el puerto (por ejemplo el 3000): 
    netstat -ano | findstr :3000
    👉 El número final es el PID (Identificador del Proceso).
  2. Comprobar qué programa es: 
    tasklist /FI "PID eq 12345"
  3. Finalizar el proceso: 
    taskkill /PID 12345 /F
    ⚠️ Usa /F para forzar el cierre.

⚙️ Alternativa universal (con npm)

Si prefieres una forma más sencilla, instala el paquete kill-port: 

npm install -g kill-port
npx kill-port 3000
Lo instalas y luego con una sola orden matas la conexión si la hay.

✅ Consejo final

Una vez liberado el puerto, ejecuta de nuevo: 

npm run dev

Si el servidor arranca sin errores, significa que el puerto ya estaba libre. Este procedimiento es muy útil cuando tienes varios proyectos Express o React abiertos a la vez.

🧠 Paso 7. Crear el controlador productos.controller.js

Ahora que ya tenemos las rutas (los caminos de la API), necesitamos decirle al servidor qué debe hacer cuando alguien accede a esas rutas. Esa es la función del controlador.

📘 ¿Qué es un controlador?

Un controlador es un archivo JavaScript que contiene las funciones que se ejecutan cuando el servidor recibe una petición HTTP. Es decir: cuando alguien accede a /api/productos, el controlador se encarga de decidir qué responder.

📦 En resumen: Ruta → Controlador → Respuesta.
La ruta detecta la URL, el controlador realiza la acción y envía el resultado al cliente.

🔗 Relación entre ruta y controlador

En el archivo de rutas escribimos algo así:

route.get('/', productosController.listarProductos);

Esto significa que cuando alguien visite /api/productos con el método GET, Express llamará automáticamente a la función listarProductos() dentro del controlador.

🧩 Estructura básica de un controlador

  • 1️⃣ Importa el modelo (para acceder a la base de datos).
  • 2️⃣ Crea una clase o un objeto con las funciones necesarias (listar, crear, actualizar, eliminar).
  • 3️⃣ Exporta esa clase u objeto para poder usarlo desde las rutas.

📁 Archivo: controllers/productosController.js

// src/controllers/productos.controller.js
class ProductosController {
  listarProductos = async (req, res) => {
    res.status(200).json({ status: 'ok', mensaje: 'Listado de productos' });
  };

  crearProducto = async (req, res) => {
    res.status(201).json({ status: 'ok', mensaje: 'Producto creado' });
  };

  obtenerProducto = async (req, res) => {
    res.status(200).json({ status: 'ok', mensaje: `Obteniendo producto con ID ${req.params.id}` });
  };

  actualizarProducto = async (req, res) => {
    res.status(200).json({ status: 'ok', mensaje: 'Producto actualizado' });
  };

  eliminarProducto = async (req, res) => {
    res.status(200).json({ status: 'ok', mensaje: 'Producto eliminado' });
  };
}

export default new ProductosController();

✔️ En resumen:

  • El router define los caminos (/api/productos, /api/productos/:id...).
  • El controlador dice qué debe pasar en cada uno (consultar, crear, actualizar o borrar).
  • El modelo (que veremos enseguida) se encarga de hablar con la base de datos.

De esta forma, separamos la lógica en capas más claras y fáciles de mantener.

⏳ ¿Por qué usamos async y await en los controladores?

Cuando un controlador usa funciones que tardan un tiempo (por ejemplo, pedir datos a MongoDB o escribir en la base de datos), esas operaciones no se hacen al instante. Si no las marcamos como “asíncronas”, el programa seguiría adelante sin esperar la respuesta.

💡 Ejemplo real

Cuando hacemos esto en el controlador:

const productos = await Producto.find();

Estamos diciéndole a JavaScript: 👉 “Espera a que MongoDB termine de buscar los productos antes de seguir con la siguiente línea”.

🔹 Qué significa async

La palabra clave async se pone delante de una función para indicar que dentro de ella se usarán operaciones asíncronas (que pueden tardar). Es decir, funciones que no se ejecutan de inmediato, como llamadas a bases de datos o peticiones HTTP. 

async function listarProductos(req, res) {
  const productos = await Producto.find();
  res.json(productos);
}

🔹 Qué hace await

La palabra await significa literalmente “espera”. Hace que el programa se detenga momentáneamente en esa línea hasta que la promesa (la respuesta de la BD) se complete. Sin await, el servidor seguiría ejecutando el código antes de tener los datos.

⚙️ Sin async/await (ejemplo incorrecto)

function listarProductos(req, res) {
  const productos = Producto.find(); // ❌ Esto devuelve una promesa, no los datos
  res.json(productos);               // Se ejecuta antes de que termine la consulta
}

✅ Con async/await (correcto)

async function listarProductos(req, res) {
  const productos = await Producto.find(); // ✅ Espera la respuesta de MongoDB
  res.json(productos);
}
En resumen:
  • async → marca una función como asíncrona (puede usar await dentro).
  • await → pausa el código hasta que una operación (como Producto.find()) devuelva su resultado.
  • Se usan porque trabajar con bases de datos implica operaciones que tardan, y queremos esperar su respuesta antes de responder al cliente.

En tu servidor, casi todas las funciones que consultan MongoDB o Mongoose deben ser asíncronas, ya que los accesos a la base de datos son procesos externos que necesitan tiempo para completarse. Recuerda usar await.

🎁 BONUS — ¿Qué es una clase y qué es un objeto?

En la Programación Orientada a Objetos (POO), una clase y un objeto son dos conceptos esenciales. Para entenderlo, imagina que una clase es el molde o plano de un producto, y un objeto es la pieza real que se fabrica a partir de ese molde.

🧩 Clase → “Molde”, “receta” o “plano”

Una clase define cómo será algo: qué propiedades (datos) tiene y qué acciones (métodos o funciones) puede realizar. No crea nada por sí misma, simplemente describe cómo deben construirse los objetos de ese tipo.

Por ejemplo, podríamos definir la clase Producto que describe cómo debe ser cualquier producto de una tienda: 

class Producto {
  constructor(nombre, precio) {
    this.nombre = nombre;   // propiedad
    this.precio = precio;   // propiedad
  }

  mostrarInfo() {           // método
    console.log(`${this.nombre} cuesta ${this.precio}€`);
  }
}

Aquí estamos definiendo el "molde" de los productos, pero todavía no hemos creado ninguno. Es como tener la receta de una pizza, pero sin haberla cocinado aún.

🎁 Objeto → “Instancia” o “ejemplar real” de la clase

Un objeto es una copia real creada a partir del molde (la clase). Cuando usamos la palabra clave new, estamos diciendo: “crea una nueva versión de esta clase con estos valores”. 

const camiseta = new Producto("Camiseta verde", 19.99);
const taza = new Producto("Taza JavaScript", 9.50);

camiseta.mostrarInfo(); // 👉 "Camiseta verde cuesta 19.99€"
taza.mostrarInfo();     // 👉 "Taza JavaScript cuesta 9.5€"

En este ejemplo, camiseta y taza son objetos (instancias) distintos, aunque ambos provienen del mismo molde Producto.

📚 Diferencia rápida entre clase y objeto

ClaseObjeto
Es el molde o plano generalEs una copia concreta creada a partir de la clase
Define qué puede tener o hacerContiene valores reales y puede ejecutar sus métodos
No ocupa memoria hasta que se creaExiste en memoria con datos propios
Se define con class Nombre { ... }Se crea con new Nombre(...)

💡 Ejemplo visual

Si pensamos en una fábrica de camisetas:

  • 🧩 La clase es el molde o diseño de la camiseta (define el color, la talla y el precio).
  • 🎁 Cada objeto es una camiseta real fabricada con ese diseño (puede tener un color o talla concreta).

🧠 ¿Y por qué usamos una clase en nuestro controlador?

En el backend, usamos clases por el mismo motivo: tener un molde organizado que agrupe funciones relacionadas. Por ejemplo, un controlador puede tener varios métodos (listar, crear, eliminar, actualizar). Al reunirlos dentro de una clase, todo queda ordenado y agrupado bajo un mismo nombre. 

// Creamos la clase
class ProductosController {
  async listarProductos(req, res) { ... }
  async crearProducto(req, res) { ... }
}

// Exportamos una instancia (objeto)
export default new ProductosController();

De esta forma, cuando Express recibe una petición, puede usar la instancia del controlador: 

route.get('/', productosController.listarProductos);

Así, productosController es el objeto real que contiene las funciones de la clase ProductosController. Es una práctica profesional para mantener el código limpio, escalable y fácil de mantener.

Paso 8. Probando rutas — Controlador básico

Antes de conectar con la base de datos, vamos a comprobar que nuestro servidor y las rutas funcionan correctamente.

📚 Cómo se conecta con la ruta

En el archivo productos.routes.js puedes asociar cada ruta con el método correspondiente del controlador. Es muy importante que los métodos que llamas en las rutas coincidan con las de tu controlador.

Para ello crearemos un controlador de prueba que solo devolverá mensajes simples. Así podremos ver la comunicación completa entre el cliente y el servidor.

🔗 Conexión con las rutas

Este controlador se usa en el archivo productos.routes.js para responder a las peticiones. Cada ruta ejecuta uno de estos métodos y devuelve un mensaje “ok”. 


    // src/routes/productos.routes.js
import { Router } from 'express';
import productosController from '../controllers/productos.controller.js';

const route = Router();

// GET /api/productos         → listarProductos
route.get('/',     productosController.listarProductos);

// POST /api/productos        → crearProducto
route.post('/',    productosController.crearProducto);

// GET /api/productos/:id     → obtenerProducto
route.get('/:id',  productosController.obtenerProducto);

// PUT /api/productos/:id     → actualizarProducto
route.put('/:id',  productosController.actualizarProducto);

// DELETE /api/productos/:id  → eliminarProducto
route.delete('/:id', productosController.eliminarProducto);

export default route;

🧭 Paso previo — Conectar las rutas en el servidor

Antes de probar con Thunder Client, tenemos que asegurarnos de que nuestro servidor “conoce” las rutas que hemos creado. Si no las importamos en el archivo principal (server.js o app.js), Express no sabrá qué hacer cuando lleguen las peticiones.

📁 Archivo: src/server.js

import express from 'express';
import cors from 'cors';

// 🔹 Importamos la ruta de productos
import productosRoutes from './routes/productos.routes.js';

const app = express();

// 🔹 Middleware: permite leer JSON en las peticiones
app.use(express.json());
app.use(cors());

// 🔹 Montamos las rutas bajo un prefijo común
app.use('/api/productos', productosRoutes);

// 🔹 Ruta de prueba opcional
app.get('/', (req, res) => {
  res.send('Servidor funcionando correctamente ✅');
});

// 🔹 Arrancamos el servidor
const PORT = process.env.PORT || 4000;
app.listen(PORT, () => {
  console.log(`🚀 Servidor activo en http://localhost:${PORT}`);
});

🧠 Explicación paso a paso

  • 1️⃣ Importamos las dependencias (express, cors) y la ruta que queremos activar (productosRoutes).
  • 2️⃣ Activamos el middleware express.json() para poder leer datos en formato JSON enviados desde Thunder Client.
  • 3️⃣ Conectamos las rutas al servidor con app.use('/api/productos', productosRoutes). Esto significa que cualquier petición que empiece por /api/productos se gestionará por el archivo productos.routes.js.
  • 4️⃣ Iniciamos el servidor con app.listen().

🔗 Relación entre archivos

server.js  →  rutas/productos.routes.js  →  controllers/productosController.js

🎯 Ahora sí: con esta conexión activa, ya puedes abrir Thunder Client y probar las rutas. Si todo está bien, deberías ver respuestas como {"status":"ok","mensaje":"Listado de productos"} o {"status":"ok","mensaje":"Producto creado"}.

🧪 Probando nuestras rutas — GET, POST, PUT y DELETE

Ha llegado el momento de comprobar que nuestras rutas y controladores están funcionando correctamente. Aún no nos conectamos con la base de datos, pero ya podemos simular las peticiones y ver las respuestas que envía el servidor.

⚙️ Cómo probar el servidor

  1. Ejecuta tu servidor con npm run dev o node src/server.js.
  2. Abre tu navegador y escribe la dirección http://localhost:4000/api/productos.
  3. Verás un mensaje como este: 
    {
  "status": "ok",
  "mensaje": "Listado de productos"
}
    Esto indica que tu ruta GET funciona correctamente.

💡 Importante: el navegador solo puede enviar peticiones GET. Para probar las rutas POST, PUT y DELETE necesitamos una herramienta especial que nos permita elegir el método de la petición y enviar datos en formato JSON.

⚡ Usar Thunder Client

Thunder Client es una extensión gratuita de Visual Studio Code que permite probar APIs directamente desde el editor. Es una herramienta muy visual, perfecta para empezar a trabajar con APIs REST.

🧩 Instalación paso a paso

  1. Abre Visual Studio Code.
  2. Haz clic en el icono de Extensiones (barra lateral izquierda o Ctrl + Shift + X).
  3. Busca “Thunder Client” (autor: Rangav).
  4. Pulsa Instalar.
  5. Después verás un nuevo icono ⚡ en la barra lateral izquierda.

🚀 Cómo usarlo

  1. Haz clic en el icono ⚡ de Thunder Client.
  2. Pulsa “New Request” para crear una nueva prueba.
  3. Elige el método HTTP: GET, POST, PUT o DELETE.
  4. Escribe la URL de tu servidor, por ejemplo:
    http://localhost:4000/api/productos
  5. Haz clic en Send y observa la respuesta del servidor.
  6. Si estás probando POST o PUT, abre la pestaña Body → JSON y escribe algo como: 
    {
  "nombre": "Camiseta azul",
  "precio": 15.99,
  "stock": 10
}

🧠 BONUS — Cómo ver quién está usando un puerto y cerrar la conexión

A veces, cuando intentas arrancar el servidor, aparece un error como: 

Error: listen EADDRINUSE: address already in use :::3000

Esto significa que **otro proceso ya está usando el mismo puerto** (por ejemplo, un servidor anterior que no se cerró correctamente).

💻 En Windows (PowerShell o CMD)

  1. Ver quién usa el puerto (por ejemplo el 3000): 
    netstat -ano | findstr :3000
    👉 El número final es el PID (Identificador del Proceso).
  2. Comprobar qué programa es: 
    tasklist /FI "PID eq 12345"
  3. Finalizar el proceso: 
    taskkill /PID 12345 /F
    ⚠️ Usa /F para forzar el cierre.

🍏 En macOS o Linux (Terminal)

  1. Listar procesos que usan el puerto: 
    lsof -i :3000
  2. Cerrar el proceso por su PID: 
    kill 12345
    (O forzar el cierre con kill -9 12345)
  3. Comando rápido para hacerlo de una vez: 
    kill -9 $(lsof -t -i:3000)

⚙️ Alternativa universal (con npm)

Si prefieres una forma más sencilla, instala el paquete kill-port: 

npm install -g kill-port
npx kill-port 3000

✅ Consejo final

Una vez liberado el puerto, ejecuta de nuevo: 

npm run dev

Si el servidor arranca sin errores, significa que el puerto ya estaba libre. Este procedimiento es muy útil cuando tienes varios proyectos Express o React abiertos a la vez.
