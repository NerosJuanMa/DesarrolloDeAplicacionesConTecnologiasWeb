Tema 1

¿Qué es una base de datos?

Manual didáctico : definición, utilidad, tipos, ejemplos, buenas prácticas y ejercicios — enfoque Full Stack.

⬅ Volver al índice Siguiente tema ➜

1️⃣ ¿Qué es una base de datos?

Una base de datos (BBDD) es un conjunto organizado de información o datos estructurados que se almacenan en un sistema informático y que pueden consultarse, modificarse y gestionarse fácilmente. Su objetivo principal es guardar información de forma ordenada, segura y accesible, para que podamos buscarla, actualizarla o analizarla cuando la necesitemos.

Ejemplo: en una red social, la base de datos guarda usuarios, publicaciones, comentarios y “likes”.

2️⃣ ¿Para qué sirve una base de datos?

Para almacenar, organizar y gestionar información de manera eficiente: consultas, actualizaciones, eliminaciones, seguridad, relaciones y escalabilidad.

  • Guardar información de forma segura y permanente.
  • Buscar y filtrar datos rápidamente.
  • Relacionar información entre distintos elementos.
  • Evitar duplicidad y errores.
  • Permitir que el proyecto crezca sin desorganizarse.

3️⃣ ¿Qué aporta al desarrollo Full Stack?

  • Persistencia real de datos.
  • Backend sólido y conectable al frontend.
  • Escalabilidad y profesionalización del proyecto.

4️⃣ Alternativas a las BBDD

  • Archivos JSON/texto plano
  • Variables en memoria
  • Hojas de cálculo
  • APIs externas

Útiles sólo al inicio o en proyectos pequeños porque no ofrecen la misma robustez y escalabilidad que una base de datos adecuada.

5️⃣ Tipos de bases de datos

Internas vs externas

  • Internas (embebidas): p. ej. SQLite (un archivo, sin servidor).
  • Externas (cliente-servidor): MySQL, PostgreSQL, MongoDB…

Relacionales vs No relacionales

  • Relacionales (SQL): tablas, filas, columnas.
  • No relacionales (NoSQL): documentos JSON, clave-valor, grafos o columnas anchas.

⚖️ ACID vs BASE: Dos maneras de manejar la información 💾

Imagina que una Base de Datos (BBDD) es como un sistema para guardar y gestionar información (dinero, fotos, posts). Hay dos filosofías principales sobre cómo debe hacerlo, dependiendo de lo que sea más importante:

🛡️ ACID: ¡Máxima Seguridad! (Piensa en un Banco 🏦)

Esta filosofía dice que la exactitud es lo más importante. Es mejor que el sistema se detenga un momento antes de permitir un error. Es muy estricta.

  • Atomicidad: La operación es "todo o nada". Si transfieres dinero, o llega completo o se queda donde estaba. Nunca se pierde.
  • Consistencia: Mantiene las reglas. Si la cuenta no puede estar en números rojos, la BBDD no lo permite. Siempre ordenado.
  • Aislamiento: Las operaciones no se estorban. Si tú pagas y otra persona cobra a la vez, no hay confusión. No se mezclan.
  • Durabilidad: Una vez que se guarda algo, queda guardado para siempre, aunque se vaya la luz. Recuerdo perfecto.

Resultado: Datos súper confiables, perfectos para sistemas críticos como la Banca.

🚀 BASE: ¡Máxima Velocidad! (Piensa en Twitter/X 🐦)

Esta filosofía dice que lo más importante es que el sistema esté siempre disponible y sea muy rápido, incluso si hay pequeños retrasos en los datos.

  • Básicamente Disponible: El sistema casi nunca falla. Aunque haya problemas, la web sigue funcionando. Siempre en línea.
  • Estado Suave (Soft State): Los datos pueden cambiar solos mientras viajan por el sistema. No son fijos en el segundo exacto.
  • Consistencia Eventual: Tarde o temprano, todos verán el mismo dato. Si publicas algo, tus amigos lo verán en unos segundos, no necesariamente al instante. Se arregla solo después.

Resultado: Sistema muy rápido y escalable, perfecto para sitios con mucho tráfico como Redes Sociales.

Conclusión: ¿Necesitas exactitud perfecta? Usa ACID. ¿Necesitas que nunca se caiga y sea muy rápido? Usa BASE.

🧱 Normalización vs Desnormalización: ¿Cómo guardamos los datos?

Una Base de Datos (BBDD) tiene que decidir si es más importante ahorrar espacio y evitar errores o si es más importante ser muy, muy rápida al leer la información.

📐 Normalización (Ahorrar y Ordenar)

Piensa en esto como una biblioteca muy organizada. Solo se guarda cada dato una sola vez. Esto se usa mucho en las BBDD SQL (Relacionales).

  • ¿Qué hace? Evita repetir información. Si tienes 100 alumnos de "Sevilla", la palabra "Sevilla" se guarda solo una vez en una tabla de "Ciudades" y los alumnos solo guardan el ID de esa ciudad.
  • Ventaja: Si "Sevilla" cambia de nombre, solo lo editas en un lugar. ¡Cero errores!
  • Desventaja: Para saber la ciudad de un alumno, la BBDD tiene que mirar dos tablas, lo que la hace un poco más lenta al leer.

Objetivo Principal: Mínima Duplicidad y Máxima Integridad (Datos limpios).

📦 Desnormalización (Duplicar para Acelerar)

Piensa en esto como una carpeta donde todo está junto. El mismo dato se puede repetir varias veces. Esto se usa mucho en las BBDD NoSQL.

  • ¿Qué hace? Duplica datos intencionalmente. Si 100 alumnos son de "Sevilla", la palabra "Sevilla" se escribe 100 veces en los registros de los alumnos.
  • Ventaja: Para saber la ciudad de un alumno, la BBDD no tiene que buscar en otra tabla; la lee directamente. ¡Es muy rápido!
  • Desventaja: Si "Sevilla" cambia de nombre, tienes que editar 100 registros. Hay más riesgo de que quede un error.

Objetivo Principal: Máxima Velocidad en Lectura y Escalabilidad (Sitios web muy grandes).

9️⃣ Ejemplos Prácticos: ¡Manos a la Obra!

Ahora que entendemos las filosofías (ACID y BASE), veamos cómo se traduce eso en el código de los dos tipos principales de bases de datos:

SQL (MySQL/PostgreSQL) - El Estricto 📐

Usan el lenguaje SQL (Structured Query Language). Aquí todo es en forma de tablas muy organizadas.

CREATE TABLE alumnos (...)

Explicación: Esto es como crear una hoja de cálculo (tabla). Defines exactamente cuántas columnas tendrá, cómo se llamarán (nombre, edad, ciudad) y qué tipo de dato guardará cada una (solo números, solo texto, etc.).

INSERT INTO alumnos (...) VALUES ('Ana López', 20, 'Sevilla');

Explicación: Agregas una nueva fila a la tabla, siguiendo el orden y los tipos de datos que definiste al inicio. Si intentas meter texto en el campo edad, ¡te dará un error! (Esto es parte de la Consistencia ACID).

SELECT id, nombre, ciudad FROM alumnos WHERE edad >= 20;

Explicación: Haces una pregunta a la BBDD: "Tráeme el ID, el nombre y la ciudad de todos los alumnos que tengan 20 años o más".

MongoDB - El Flexible 📦

Es una BBDD NoSQL que guarda la información en formato de documentos (parecido a archivos JSON). Es más flexible.

db.alumnos.insertMany([ { nombre: "Ana López", edad: 20, ciudad: "Sevilla" }, 
              { nombre: "Luis Díaz", correo: "luis@example.com" } ]);

Explicación: Agregas documentos a la "colección" (como si fuera una carpeta de archivos). Fíjate: ¡El documento de Ana tiene un campo 'ciudad', pero el de Luis tiene un campo 'correo' que Ana no tiene! Esta flexibilidad es clave en NoSQL.

db.alumnos.find({ edad: { $gte: 20 } }, { nombre: 1, ciudad: 1 });

Explicación: Busca todos los documentos de alumnos donde la edad sea mayor o igual a 20. Pídele que solo te muestre los campos 'nombre' y 'ciudad'.

db.alumnos.updateOne({ nombre: "Ana López" }, { $set: { ciudad: "Córdoba" } });

Explicación: Encuentra el documento de Ana López y actualiza su campo 'ciudad' a 'Córdoba'.

Diferencia clave para el alumno nuevo: En SQL tienes que definir todo muy bien antes de empezar. En MongoDB/NoSQL puedes empezar a guardar información, aunque los documentos no sean exactamente iguales.

❓ Preguntas frecuentes (FAQ)

¿Puedo empezar con JSON y migrar después?

Sí. Prototipa con JSON y migra a SQL/Mongo cuando crezca.

¿SQL es “mejor” que NoSQL?

Depende: SQL prioriza integridad; NoSQL flexibilidad y escalado.

¿Qué elijo para mi primer CRUD?

Para relaciones/consultas: SQL. Para iterar rápido: MongoDB.
